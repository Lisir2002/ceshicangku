## 1. 协作总则（三条铁律）

这一节是你提出的三条要求，我把它固化为可执行、可检查的规则。

### 铁律一 · 技术不可自我捏造，必须联网求证

> 任何进入方案的技术、函数、API、语法、兼容性结论，都必须有可追溯的联网来源，不得凭印象编造。

- 不允许出现"我记得大概是……""通常这样做"这类无来源的技术断言。
- 涉及具体函数 / 参数 / 版本特性时，必须能给出官方文档或权威来源链接。
- 拿不准的一律标注为**待验证**，并在动手前先验证，而不是"先写了再说"。

### 铁律二 · 严格按需求实现，需拍板必须提问

> 只做你明确要求的事，不做自作主张的扩展；遇到需要你做决定的分叉点，先问、再动。

- **不擅自加功能、不擅自改需求、不擅自"顺便优化"**。
- 出现以下情况必须停下来向你提问，而不是自己替你决定：
  - 需求有歧义、存在两种以上合理理解；
  - 涉及技术选型、架构、第三方依赖；
  - 涉及数据模型 / 字段 / 权限设计；
  - 涉及 UI 风格、配色、交互方式的取舍；
  - 涉及需要账号、密钥、服务器、域名等外部资源。
- 提问时**必须给出选项 + 各选项的优缺点 + 我的推荐**，而不是开放式的"你想要什么？"。

### 铁律三 · UI/UX 必须联网学习，追求最佳视觉与交互

> 界面设计不靠臆想，配色、排版、交互都要基于经过验证的通用设计方法与可访问性标准。

- 配色必须有依据（色彩比例法则、对比度标准），而不是随意挑颜色。
- 交互必须有依据（可用性启发式、状态完整性），而不是"能点就行"。
- 所有界面需通过本文档第 4.4 节的 UI/UX 检查清单。

## 2. 技术求证流程（铁律一落地）

### 2.1 可信来源分级

| 级别 | 来源 | 可否作为最终依据 |
| --- | --- | --- |
| A 级 | 官方文档（php.net 手册、MySQL 官方手册、W3C 规范） | ✅ 可直接采信 |
| B 级 | 官方 RFC / 发布公告 / EOL 时间表 / 安全公告 | ✅ 可直接采信 |
| C 级 | 知名技术社区 / 一线工程博客（内容与 A/B 级一致时） | ⚠️ 需与 A/B 级交叉印证 |
| D 级 | 论坛零散回答、AI 生成内容、无出处转载 | ❌ 不可单独作为依据 |

### 2.2 求证四步法

1. **定位**：明确要验证的具体事实（函数名？参数？版本下限？行为？）。
2. **检索**：优先查官方文档；官方无记录再降级到 C 级并交叉验证。
3. **交叉印证**：至少 1 个 A/B 级来源与 1 个其他来源一致，方可定论。
4. **落档**：把"结论 + 来源链接 + 版本适用性 + 置信度"写进本文档或对应技术说明。

### 2.3 结论标注规范

技术结论一律采用如下格式，便于你核对：

```
结论：<可直接执行的结论>
来源：<官方/权威链接>
适用版本：<PHP 5.6 / MySQL 5.5.3+ 等>
置信度：确定 / 较确定（已交叉验证）/ 待验证
```

### 2.4 禁止行为清单

- ❌ 编造不存在的函数、参数、配置项。
- ❌ 把新版本（PHP 7/8）的特性当作 PHP 5.6 可用。
- ❌ 声称"已验证"但实际未联网核实。
- ❌ 用"应该可以""理论上没问题"替代验证结论。

## 4. UI/UX 设计规范（铁律三落地）

> 说明：以下原则来自 Nielsen Norman Group 可用性启发式、W3C WCAG 2.2 可访问性规范与主流 UI 色彩方法论，均在第 10 节附来源。

### 4.1 视觉设计 · 配色

**（1）60-30-10 色彩比例法则**（控制视觉权重与层级）

- **60% 主色 / 背景色**：低饱和、中性或浅色调，作为大面积底色，不抢视觉、不造成疲劳。
- **30% 次色**：用于分区、卡片、次级按钮，形成结构与节奏。
- **10% 强调色**：用于主按钮、关键操作、当前位置，用来"指挥视线"。

**（2）对比度硬性标准（WCAG 2.2）**

| 内容类型 | 最低对比度 |
| --- | --- |
| 正文文字（<18px 或 <14px 加粗） | **4.5:1** |
| 大号文字（≥18px 或 ≥14px 加粗） | **3:1** |
| UI 组件 / 图标等非文本内容 | **3:1** |
| 焦点指示器（聚焦前后同像素对比） | **3:1** |

- **颜色绝不能作为唯一的信息载体**（如不能只用红色表示错误，需配图标/文字）。
- 需做色盲（红绿色觉异常）模拟检查。

### 4.2 视觉设计 · 设计令牌（Design Tokens）

**令牌接口层（你的决定：D-006 —— 风格后续定，先留接口）**

为满足"视觉风格后续讨论、可替换"的要求，本项目采用**令牌接口层**设计：

- 所有颜色、字号、间距、圆角、阴影、动效时长都收敛到**一层命名令牌**（如 `--color-primary`、`--space-4`、`--radius-md`）。
- 业务页面/组件**只引用令牌名，不写具体数值**。
- 将来切换风格时，**只改令牌定义文件一处**，全站视觉随之更新，不动业务代码。
- 输出方式：优先 CSS 变量（`assets/css/tokens.css`）；若需服务端控制，可用 PHP 常量/配置统一输出为 CSS 变量。

| 令牌类别 | 建议内容 |
| --- | --- |
| 颜色 | 主色、次色、强调色、成功/警告/危险/信息色、文字主/次/禁用、边框、背景层级（3 层以内） |
| 字号 | 基于一套模数比例（如 1.25 倍）建立 6–8 级：正文 16px 起，行高 1.5–1.7 |
| 间距 | 8px 栅格体系：4 / 8 / 12 / 16 / 24 / 32 / 48 |
| 圆角 | 统一 2–3 档（如 4 / 8 / 12px） |
| 阴影 | 统一 2–3 档（卡片 / 悬浮 / 弹层） |
| 动效时长 | 微交互 150–200ms，过渡 200–300ms；缓动用 ease-out 系 |

> 注：字号、间距、圆角的**体系**已在结构层确立；首版**主题定稿**为 D-029「天空 + 磨砂玻璃」（配色取自用户提供的天空背景图，磨砂玻璃用半透明白 + `backdrop-filter`），数值与令牌均已落地到 `assets/css/tokens.css`，后续仍可单点换肤。

### 4.3 交互设计

**（1）Nielsen 十大可用性启发式（逐条作为验收项）**

1. **系统状态可见**：任何耗时操作都要有反馈（加载、进度、禁用态）。
2. **贴合真实世界**：用用户的语言，不用系统术语。
3. **用户可控与自由**：要有明确的取消 / 返回 / 撤销出口，杜绝"死胡同"。
4. **一致性与标准**：同类元素同类样式，遵循平台与站内既有约定。
5. **错误预防**：优先防止错误发生（约束、默认值、二次确认），而非事后报错。
6. **识别优于回忆**：选项可见，不要让用户去记。
7. **灵活与高效**：为熟练用户提供快捷路径（快捷键、记住选择）。
8. **美学与极简**：界面只保留必要信息，去除干扰。
9. **帮助用户识别与修复错误**：错误信息要**说人话 + 指出位置 + 给出解法**。
10. **帮助与文档**：关键流程提供就地帮助。

**（2）状态完整性（每条列表/表单/请求都要覆盖）**

| 状态 | 要求 |
| --- | --- |
| 初次加载 | 骨架屏或加载指示；**仅当无数据可显示时**才显示 loading |
| 刷新/更新 | 已有数据时用轻量刷新提示，不整屏闪烁 |
| 空状态（基线） | 友好引导（用户还没建任何东西） |
| 无结果（筛选/搜索） | "没找到" + 建议（换关键词/清除筛选） |
| 错误 | 可重试 + 说明原因；错误可关闭或自动消失 |
| 成功 | 轻量确认反馈，不打断操作流 |

**（3）表单与微交互**

- 每个字段有：标签、示例、聚焦态、校验错误态、错误原因。
- 提交按钮要防重复提交（提交中禁用 + 文案变化）。
- **登录提交的具体规格（D-030）**：空值 / 格式不符由前端**直接判断**，就地逐字段提示（红字 + 红框 + 聚焦首个错误字段），**不进入加载态、不整页提交**；通过校验后，加载态**只做在按钮内**（圆形旋转 + 文案「验证中 → 登录中」，按钮禁用），**不做整页遮罩**。
- 微交互只服务于反馈与引导，不做无意义动画。

**（4）可访问性（原生 HTML/CSS 也完全能做）**

- 语义化标签（`header/nav/main/section/button/label`），不滥用 `div`。
- 所有可交互元素**键盘可达**，`Tab` 顺序合理，`focus` 可见。
- 图片有 `alt`；表单控件与 `label` 正确关联。
- 不依赖纯 hover 传递关键信息。

### 5.3 安全基线（PHP 5.6 环境）

**（1）SQL 注入防护 · 强制使用 mysqli 预处理语句**

- 所有含用户输入的查询一律用 `prepare()` + `bind_param()`，**禁止字符串拼接 SQL**。
- 绑定参数**无需手动转义**，因为参数与查询模板分离传输（来源：PHP 官方手册）。
- SQL 注入的纵深防御：永远不用超级用户/库属主连接，使用**最小权限**的专用账号；校验输入类型（`is_numeric`、`ctype_digit`、正则）。

```php
// 参考写法（PHP 5.6 可用）
$mysqli = new mysqli('localhost', $user, $pass, 'app_db');
$mysqli->set_charset('utf8mb4');            // 连接后、执行任何 SQL 前立即设置

$stmt = $mysqli->prepare('SELECT id,name FROM users WHERE username = ? AND status = ?');
$stmt->bind_param('ss', $username, $status); // 's'=string 'i'=int 'd'=double 'b'=blob
$stmt->execute();
```

**（2）密码存储 · password_hash / password_verify**

- 永远不明文存储，也不用 `md5` / `sha1`。
- `password_hash()` 默认 bcrypt（含盐、含成本因子），`password_verify()` 校验。**二者自 PHP 5.5 起可用，5.6 完全支持**。

**（3）CSRF 与 XSS**

- 会话 Cookie 尽量设置 `HttpOnly`（降低 XSS 窃取会话风险）。
- **SameSite 注意事项**：`setcookie()` 的 `samesite` 参数与相关 ini 项是较新版本才加入的，**PHP 5.6 的正规 API 不支持**，需通过手动输出 `Set-Cookie` 头来附加 `SameSite=Lax/Strict`（属较确定、需实测）。
- 表单使用一次性 CSRF Token 并在服务端校验；退出/敏感操作要求二次确认。
- 输出到 HTML 一律做转义（`htmlspecialchars`，注意指定 `ENT_QUOTES, 'UTF-8'`），防止 XSS。

**（4）随机令牌生成（PHP 5.6 陷阱）**

- `random_bytes()` 是 **PHP 7.0** 才加入的，5.6 没有；推荐用 `openssl_random_pseudo_bytes()`（需 openssl 扩展）生成 CSRF / 会话令牌。
- 需要抗时序攻击的字符串比较（如 Token、签名），使用 `hash_equals()`（**PHP 5.6.0 起可用**）。
